## 2. 产品定位与设计哲学（理解错，全做错）

**Coomi Deck 是跨设备 agent 协同调度控制台——调度层，不是执行层。** 桌面 CLI agent 工具（zcode、codex 等）是被注册、被派发、被回收的子代理；Coomi 引擎内置其中，是协调者，也直接处理零散任务；用户以架构师视角统揽全局：看进度、做审批、派任务、收结果。价值观排序：**自动化 > 便携性 > 稳定性**；界面承诺舒适、方便、高效。多端协同走用户自有基础设施（CoomiLink），不经过第三方云。

**核心哲学：Coomi 不设计方案。** Coomi 只精确描述"现在的问题"和"要达到的目标"，方案设计交给专业 agent，结果回流后呈给用户。落地到界面语言：

- 所有派发/模板/工作流节点表单只问三件事：**问题描述、目标描述、资源与约束**——不提供"解决方案步骤"输入位。
- 审批卡片呈现 agent 的方案摘要与依据，不是 Coomi 的二手加工意见。
- 迭代可溯源：每次派发记录所用提示词的版本。

**色彩语义规则（全产品最高优先级的视觉法则）：冷蓝 = 机器流转，暖橙 = 人工决策点。** 蓝色表达"自动化在跑"（代理、运行中、系统动作）；橙色只在"需要人"时出现（审批、资源申请、代理请求）；红色仅表示失败/异常。用户扫一眼即可分辨"机器的事"和"我的事"。

**协议对齐 A2A**：任务状态机采用 `submitted → working → input-required → completed / failed / canceled`；`input-required` 即等待审批/输入。代理能力以 AgentCard 概念呈现。

## 3. 实体模型（8 个，用户面向词汇）

| 实体 | 定义 |
|---|---|
| 工作流 Workflow | 可复用 DAG 配置；节点 = 任务步骤（代理指派、提示词模板、审批门） |
| 任务 Task | 一次执行实例，统一任务流的单元；来源：工作流运行 / 单次派发 |
| 步骤 Step | 工作流任务内某节点的单次执行 |
| 代理 Agent | 注册的执行单元；Coomi 引擎为内置特殊代理 |
| 审批 Approval | 决策请求，三类：工作流审批门 / 代理运行时请求 / 资源申请 |
| 产物 Artifact | 任务的结构化产出，附属任务 |
| 提示词 Prompt | 核心资产。两类：**任务模板**（问题+目标+默认代理+关联资源+变量槽，有版本历史）、**方法论偏好**（常驻注入、单次可停用） |
| 资源 Resource | 服务器/密钥/GPU/API 额度；挂"使用指令"（口述用法→精炼为提示词）；带审批策略（人工审 / 自动放行规则） |

## 4. 信息架构（已定）

- **一级导航 7 项**：控制台 / 任务 / 工作流 / 提示词 / 代理 / 资源 / 设置。
- **三栏骨架**：左导航（196px）+ 主内容区 + 右侧 Coomi 面板（VS Code 副侧栏范式：横向可拖宽 264–560px 并持久化，⌘J 收起，窗口 <1380px 默认自动收起）。Coomi 面板是用户与 Coomi 的指挥通道，输入框支持 `@` 引用资源、`#` 引用模板。
- **控制台 = 箱庭式两侧布局**：
  - 左侧主体：**运行中的工作流**——每张运行卡片内嵌 DAG 节点状态条（节点按状态着色：完成绿/进行中蓝脉冲/等待审批橙/失败红，审批门前橙色虚线连接）+ 进度条 + 已运行时长；下方单次任务小卡片。
  - 右侧主体：**选中工作流详情**（节点步骤轨 + 节点级干预按钮 + 实时日志尾窗）+ **待审批清单**（三类审批卡片，就地决策，处理后移入"已处理"）。
  - 设计意图：审批挂在具体工作流上下文里，先看"卡在哪"再决策。
- **⌘K 命令面板是一等公民**；键盘流目标：纯键盘 30 秒清空收件箱。
- 顶部状态条：代理在线数 · 运行中 · 异常数 · CoomiLink 同步指示 · 主题切换。

## 7. 设计守则（违反 = 返工）

1. **颜色只写语义令牌**，禁止硬编码色值；新增语义色先加进 packages/tokens 四主题。
2. 新组件**先复用 global.css 原语**（btn/badge/dot/card/chip/progress），确有必要再新建，并保持同样的令牌化写法。
3. **蓝橙语义不可破**：自动化/机器 = accent 蓝，需要人 = human 橙，失败 = danger 红。
4. 示例数据集中在 `stores/data.ts`，场景取自真实痛点（发布上线 Coomi Android、改官网、改后台面板、反馈分析→规划批次、GPU 申请、迭代清单归档）；不要在组件里散落假数据。
5. 交互反馈要"活的"：按钮有 hover/press、状态有脉冲、进度会走、卡片处理后有去处的动效。
6. 最小可用窗口 1280×800；任何布局改动在此尺寸下验证。
7. 改动已拍板的决策前，先向用户确认；确认后回写决策文档。
